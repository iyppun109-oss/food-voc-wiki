## 4. 현재 발생 가능한 오류 (재현 확인한 것 위주)

**보고서 생성**

1. 직접 수정 불가 (`ReportGeneratorModal.tsx:248`): 360px 화면에서 재현함
2. "고객 반응"이라는 글자를 누르면 첫 체크박스("괜찮다고 함")가 체크됨: 체크박스 묶음 전체를 `<label>`로 감싸서 생기는 문제. 같은 이유로 "현장 조치" 글자를 누르면 "고객 응대"가 체크됨. 재현함
3. 유형 오분류: 아래는 실제 실행 결과입니다

| 입력 키워드 | 고객 정보 | 판정 결과 |
|---|---|---|
| 식중독 의심 복통 | 점심시간 이용 고객 1명 | **염도** |
| 식중독 의심 복통 | 고객 1명 | 식중독 의심 |
| 피자가 덜 익음 | 고객 1명 (+ 자동 추천 사례) | **염도** |
| 양 부족 / 직원 불친절 | 점심시간 이용 고객 1명 | **염도** |
| 음식이 짬 | 고객 1명 (사례 없음) | **기타** (`짬`이 키워드에 없음) |

원인은 세 가지입니다. (a) 염도 키워드 `'간'`이 "시간, 간식, 공간"에 부분일치함 (b) 판정 순서가 고정이라 식중독·안전사고보다 염도·품절이 먼저 걸림 (c) 고객 정보, 메모, 자동 추천 사례의 본문 전체가 판정 텍스트에 섞임

4. 고객사 담당자를 비우면 "안녕하세요 **담당자님님**,"이 출력됨 (기본값 `'담당자님'`에 `님`을 한 번 더 붙임)
5. 조사 오류: `${라벨}로` 형태로 문장을 조립해서 "머리카락로", "비닐/플라스틱로", "치아 파절 의심로"가 나옴
6. 고객용 메시지에 **내부 분류 라벨이 노출**됨: "말씀 주신 안전사고 / 치아 파절 의심로…"
7. 사내 보고서의 '조치 사항' 칸에 **원인 추정 문장과 고객 반응 문장이 섞임**: "- 고객이 위생 상태 불편을 표명함."(염도 건인데 '위생'으로 나옴). `불쾌감 표현`이 모든 유형에서 "위생 상태 불편"으로 고정 변환됨
8. 사내 보고서 '발생 내용'의 줄 순서가 해시값으로 섞여 첫 줄이 "현장에서 배식 직전 표면·고정 상태를 확인함."처럼 사건 설명이 아닌 문장으로 시작함
9. 고객사 보고서가 문단이 아니라 한 줄씩 나열되고, 날짜와 관계없이 항상 "금일"이라고 씀
10. 부분문자열 중복 제거(`dedupeSentences`)가 짧은 문장을 포함한 긴 정상 문장을 지워 버릴 수 있음
11. `sanitizeOutput`이 "중문식당식당", "확인함.가" 같은 **과거 오류를 하드코딩으로 땜질**함. 근본 원인은 그대로 남아 있음
12. 사업장명이 "카페"면 "카페 식당", "구내식당 2층"이면 "구내식당 2층 식당"이 됨

**금지표현**

13. 자동 치환을 하면 마침표가 겹침: "…공유드리겠습니다**..**" (원문의 마침표가 남음)
14. 치환하면 앞뒤 문맥이 깨짐: "확인 결과 문제 없습니다." → "확인 결과 말씀 주신 사항은 추가로 확인하고 공유드리겠습니다.."
15. 승인된 보상("고객사 승인에 따라 환불해드리겠습니다")도 무조건 위험으로 표시하고 치환함
16. 생성 엔진이 스스로 만든 문장(허위 완료형, 문체 혼용, 조사 오류, 중복)은 검사 대상이 아님

**UI**

17. 360px 화면에서 모달 "닫기" 버튼이 "닫 / 기"로 세로로 쪼개짐 (재현함)
18. 카테고리 칩에 "전체"가 2개 있고, 두 번째를 누르면 결과가 0건. 요약 카드의 "주요 카테고리 수 14개"도 "전체"를 포함해서 셈
19. `index.html`의 title과 description이 이전 이름 그대로임

**Menu Lab**

20. 1~3위가 같은 메뉴의 복제본이고, 대체 메뉴도 그 복제본임 (실행 결과로 확인)
21. 세 추천안의 국과 찬이 완전히 같음 (메인 카테고리와 위험만 보고 고르기 때문)
22. 국의 `fitWith`에는 `['조식','중식']`(식사 구분)이 들어 있는데 메인 카테고리(`'한식'`)와 비교함. 따라서 국 궁합 점수는 항상 0

## 5. VOC 보고서 생성 엔진의 구조적 문제

**결론: 덧대어 고치는 방식으로는 해결되지 않습니다. 엔진을 다시 설계해야 합니다.** 단, UI와 입력 항목, 300건 DB는 그대로 두고 `reportGenerator.ts` 안쪽만 단계적으로 교체할 수 있습니다.

### 5.1 근본 원인

1. **사실 상태 모델이 없음.** 입력은 문자열과 체크박스 목록뿐이고, 엔진 안에 "확인된 사실 / 고객 주장 / 미확인 / 완료 조치 / 예정 조치 / 원인 후보"를 구분하는 구조가 없습니다. 문장 DB도 상태 태그 없이 완료형("확인함", "점검함")으로 작성되어 있어서 어떤 문장을 뽑아도 허위 완료가 생길 수 있습니다.
2. **문서 3종이 독립된 설계가 아님.** 고객용과 고객사용은 같은 유형 라벨과 같은 고정 문장을 공유하고, 사내 보고는 `ensureInternalStyle`로 "합니다."를 "함."으로 **문자열을 치환**합니다.
3. **문장 선택이 해시 기반 무작위.** `pickBySeed`가 사건, 조치, 원인, 예방, 반응 문장을 한 바구니에 넣고 해시로 N개를 뽑습니다. 그래서 '조치' 칸에 원인 문장이 들어가고 줄 순서도 매번 다릅니다.
4. **후처리 땜질이 쌓임.** `sanitizeOutput`의 하드코딩 치환, 부분문자열 중복 제거, `void reactionToClient` 같은 흔적이 남아 있습니다.
5. **유형 판정이 취약.** 첫 번째로 일치하는 키워드가 이기는 방식이고, 판정 텍스트 범위가 너무 넓습니다(4장 #3).
6. **문장 DB가 3벌**(인라인 1벌, 사용되지 않는 2벌)이고 문체도 서로 다릅니다.

### 5.2 제안 구조

```
src/report/
  types.ts            IncidentFacts, FactStatus, VocTypeId, Audience
  classify.ts         유형 판정 (키워드 + 단어 경계 + 우선순위 + 고위험 우선)
  facts.ts            폼 입력 → IncidentFacts (상태 태그가 붙은 사실 목록)
  korean.ts           조사 처리(을/를, 이/가, 은/는, 으로/로), 이름 중복 방지
  sentenceBank/       유형별 문장 DB (아래 스키마)
  compose/
    customer.ts       고객용: 합니다체 전용 조립기
    internal.ts       사내용: 음슴체 전용 조립기 + 고정 양식
    client.ts         고객사용: 공식 합니다체 문단 조립기
  validate.ts         생성 후 검사 (문체, 반복, 미완성, 허위 완료, 금지표현)
  index.ts            generateReportContents (기존 시그니처 유지)
```

**IncidentFacts의 핵심 구조**

```ts
type FactStatus = 'confirmed' | 'claimed' | 'unverified' | 'done' | 'planned' | 'hypothesis'

interface IncidentFacts {
  type: VocTypeId                 // 'hair' | 'insect' | ... | 'tooth_injury' | 'foodborne'
  risk: 'normal' | 'caution' | 'critical'
  menu?: string
  claim: string                   // 고객이 제보한 내용 (claimed)
  doneActions: OnsiteActionId[]   // 사용자가 체크한 것만 done
  plannedActions: OnsiteActionId[]// 유형 규칙에서 나온 권장 조치 (planned)
  reactions: CustomerReaction[]   // 전부 반영
  memo?: string
}
```

**문장 DB 한 건의 스키마**

```ts
interface SentenceEntry {
  id: string
  type: VocTypeId | '*'
  slot: 'incident' | 'action' | 'cause' | 'prevention' | 'greeting' | 'apology' | 'followup'
  audience: Array<'customer' | 'internal' | 'client'>
  status: FactStatus              // 이 문장이 주장하는 사실 상태
  requires?: OnsiteActionId[]     // 이 조치가 done일 때만 사용
  excludesWhen?: OnsiteActionId[] // 이 조치가 done이면 사용 금지
  variants: string[]              // 같은 의미의 다른 표현 (의미는 고정, 표현만 다양화)
  template?: boolean              // {menu}, {menu:을/를} 같은 자리표시자 포함 여부
}
```

규칙은 이렇습니다. `status: 'done'`인 문장은 `requires`가 충족될 때만 선택됩니다. 같은 입력이면 **어떤 슬롯에 어떤 사실이 들어가는지는 고정**되고, `variants` 중 어떤 표현을 쓸지만 바뀝니다. 그래서 다시 생성해도 사건 내용과 완료 조치는 그대로입니다.

### 5.3 고위험 유형 처리

- 판정 우선순위: 식중독 의심 > 안전사고(치아, 상해) > 알레르기 > 이물 > 품질 > 운영 순서. 고위험 키워드가 하나라도 있으면 일반 유형보다 우선합니다.
- 고위험 문서는 별도 조립기를 씁니다. 고객 상태 확인, 보존식과 현물 보존, 즉시 보고 문장은 **선택이 아니라 필수**로 넣습니다. 의료적 판단, 원인 단정, "안전합니다", "문제 없습니다"는 쓰지 않습니다.
- 고위험인데 '고객 상태 확인'이 체크되지 않았으면 문서 상단에 **확인 필요 항목**을 경고로 표시합니다.

### 5.4 기존 DB 활용

- `vocCases` 301건은 **유사 사례 추천과 참고 표시에만** 씁니다. 유형 판정이나 생성 문장의 원천으로는 쓰지 않습니다(현재 오분류의 원인).
- `reportTemplates.ts`의 합니다체 문장은 고객사용 `variants`로, `reportSentenceTemplates.ts`의 원인·예방 문장은 사내용 `variants`로 **선별해서 옮깁니다.** 문장마다 상태 태그를 붙이고, 비문("확인됨이 기록됨", "가능성이 있었을 가능성이 있음")은 버립니다.

## 6. 금지표현 검사의 구조적 문제

- 공백을 지운 뒤 부분일치로 검사하므로 문맥을 보지 못합니다(승인된 보상, 인용문, 부정문 구분 불가).
- 치환이 구절 단위라서 문장이 깨지고 마침표가 겹칩니다.
- 검사 영역이 '금지 구절 24개'뿐입니다. 요구사항의 문체 혼용, 반복, 미완성 문장, 허위 완료, 조사 오류는 검사하지 않습니다.
- 결과 화면에 '직접 수정' 동선이 없습니다(그리고 직접 수정 자체가 고장 나 있음).

**개선안:** 텍스트를 문장 단위로 나눈 뒤 규칙 묶음별로 검사합니다. 규칙 묶음은 `원인 단정`, `미확인 사실`, `보상 확약`, `고객 비난`, `회피`, `의료 단정`, `문체 혼용(문서 종류별)`, `반복`, `미완성`, `조사` 입니다. 각 결과에는 `{문장 위치, 발견 문구, 이유, 권장 수정문(문장 전체), 위험 수준}`을 담습니다. 치환은 **문장 전체를 바꾸는 방식**으로 하고, 치환 뒤에는 다시 검사합니다. 보상 관련 규칙에는 "승인", "기준에 따라" 같은 예외 문맥을 둡니다. 사과 표현은 화이트리스트로 관리합니다.

## 7. Menu Lab 추천 엔진의 구조적 문제

1. **데이터가 실제 속성을 갖고 있지 않음.** 반찬의 역할, 위험, 궁합이 `index % 8` 같은 공식으로 배정되어 있어서 점수가 의미 없는 값입니다. 재료, 조리법, 맛, 온도, 색 같은 속성이 없으니 "감자볶음 + 감자채볶음" 중복을 이름 그룹 4개(하드코딩)로만 막고 있습니다.
2. **복제 메뉴** 때문에 다양성이 0입니다(4장 #20).
3. 메인 데이터에 `bestSides`, `avoidSides`, `bestSoups`, `vocPrevention`이 있는데 **추천 엔진이 쓰지 않습니다.**
4. **예산:** 10,500원 이상이면 `strengths`가 4개 이상인 메뉴에 +2점을 주는 것이 전부입니다. 식단가와 식재료비를 구분하지 않고, 원가 데이터도 없습니다. 지금 화면은 "단가를 반영해 추천"한다고 안내하고 있어서 **실제보다 과장된 설명**입니다.
5. 1안, 2안, 3안의 성격(대중성, 만족도, 운영 안정성)이 없고 같은 점수표의 상위 3개를 보여 줄 뿐입니다.
6. 계절, 색감, 식감, 조리법 중복, 단백질과 채소 구성을 평가하지 않습니다.
7. 현재 데이터에 영어 문장은 없습니다(이전에 지적된 영어 혼입은 커밋 `303eb46`에서 정리된 것으로 보입니다). 다만 재발을 막는 자동 검사가 없습니다.

**개선안 요약:**

- 메뉴 항목에 `ingredients[]`, `method`(볶음, 조림, 튀김, 무침, 구이, 찜, 국물), `taste`(매운, 짠, 단, 담백), `color`, `texture`, `protein`, `season[]`, `role`(메인, 국, 찬_채소, 찬_단백, 김치) 속성을 붙입니다.
- 중복은 `재료 겹침 + 조리법 겹침 + 맛 겹침` 점수로 판정합니다.
- 추천은 "점수 상위 3개"가 아니라 **목적 함수가 다른 3안**(대중성, 만족도, 운영 안정성)으로 각각 최적 조합을 찾고, 안끼리 메인이 겹치지 않게 합니다.
- 예산은 당분간 "참고 조건"으로만 표시하고 문구도 그렇게 바꿉니다. 원가 계산용 스키마(식재료명, 규격, 단위당 가격, 1인 사용량, 수율, 식수 → 1인분 식재료비)는 별도로 설계만 해 둡니다.

## 9. 개선이 필요한 DB 구조

1. **VOC 유형 체계:** `vocCases.category`(13종), 생성기 `CategoryType`(14종), Menu Lab `VocRisk`(10종)가 모두 따로 있습니다. 유형 ID를 한 곳(`src/domain/vocTypes.ts`)에 정의하고 별칭, 위험 수준, 표시 이름을 함께 둡니다. '품질'은 `조리상태 불량`, `온도`, `맛·식감`, `시설·환경` 같은 세부 유형으로 나눌 것을 권장합니다.
2. **문장 DB:** 5.2절 스키마로 통일합니다.
3. **현장 조치 ID:** 현재 한글 문자열(`'현장 확인 중'` 등)이 타입이자 표시 문구입니다. ID와 표시 문구를 분리하고, 고위험 유형 전용 조치(현물 보존, 보존식 확인, 의료기관 안내, 본사 보고)를 추가합니다.
4. **사례 DB:** 필드와 데이터는 그대로 두고 `type`(새 유형 ID), `risk` 같은 선택 필드만 추가합니다. 짧은 항목 보강과 카테고리 재분류는 별도 작업으로 진행합니다.
5. **메뉴 DB:** 7장의 속성 추가, 복제 제거, 반찬 속성을 수작업으로 작성합니다.
6. **원가 DB(설계만):** `Ingredient { name, spec, unit, unitPrice, updatedAt }`, `RecipeLine { menuId, ingredientId, gramsPerServing, yieldRate }`. 식단가(판매가)와 식재료비를 별도 필드로 둡니다.

- 1-a 즉시 버그: 직접 수정, label 중첩, '전체' 칩 중복, 상세 라벨, 닫기 버튼 줄바꿈, 담당자님님, title과 description
- 1-b 긴급 정확도 패치: 유형 판정에 단어 경계 적용, 고위험 우선, 판정 텍스트를 키워드와 메뉴명으로 제한. Menu Lab 복제 메뉴 제거
- 1-c 테스트 기반 마련: `vitest` 추가(**새 개발 의존성이므로 승인 필요**), 대표 10개 유형×3종 = 30개 출력의 스냅샷과 규칙 검사(문체, 금지 어미, 반복, 허위 완료, 조사)
- 1-d 미사용 파일 정리, README 재작성, BOM과 줄바꿈 정규화(`.editorconfig`, `.gitattributes`)

**Phase 2. 보고서 엔진 교체**

- `IncidentFacts`, 조사 처리 모듈, 유형 판정 모듈
- 문서별 조립기 3개와 고위험 전용 흐름
- 문장 DB 이관(먼저 10개 대표 유형, 이후 나머지)
- 메모와 복수 고객 반응 반영
- 문장 단위 안전성 검사, 치환 후 재검사
- 테스트 30개가 모두 통과해야 병합

**Phase 3. Menu Lab 재설계**

- 메뉴 속성 스키마와 데이터 보강(메인 18종 이상, 반찬과 국은 수작업 속성)
- 중복 판정, 3안 목적 함수, 예산 문구 정직화
- 한국어 전용 검사와 다양성 테스트

**Phase 4. UI/UX**

- 360, 390, 430px, 태블릿, 데스크톱 점검
- 보고서 모달을 단계형(입력 → 결과)으로 구성하고 결과 탭화, 복사 피드백, 검사 결과에서 해당 문장으로 이동
- 접근성(포커스 트랩, 라벨 연결)

**Phase 5. 운영 확장 설계(문서만 작성)**

- 즉시 조치 체크리스트, 위험도, 보고 대상 추천의 데이터 구조
- VOC 이력과 월간 분석: 저장소 선택(로컬 vs 서버), 개인정보 보존 정책, 권한
- AI API 연동 아키텍처
