# VOC 보고서 생성 엔진

외부 AI를 부르지 않는 규칙 기반 엔진입니다. 입력 한 번으로 세 가지 문서를 만듭니다.

| 문서 | 문체 | 받는 사람 |
|---|---|---|
| 고객용 | 공손한 합니다체 | VOC를 낸 고객 |
| 사내 보고 | 음슴체(~함.) | 사내 보고 라인 |
| 고객사 보고 | 공식 합니다체 | 고객사 담당자 |

## 원칙

1. **사실을 만들지 않습니다.**
   - 완료형 문장(완료함, 교체해 드렸습니다)은 사용자가 '완료한 조치'에서 고른 항목으로만 만듭니다.
   - 고르지 않은 고객 반응(보상 요청, 연락처 등)은 어느 문서에도 나오지 않습니다.
   - 원인은 사내 보고의 '원인 후보 (확인 전 추정, 단정 아님)'에만, '~여부 확인 필요함' 형태로 씁니다.
   - 식중독 의심·안전사고는 원인 후보를 쓰지 않습니다.
   - 비슷한 사례(vocCases)의 본문은 보고서에 넣지 않습니다. 유형을 판정하지 못했을 때 유형만 참고합니다.
2. **문체를 섞지 않습니다.** 세 문서는 같은 내용을 서로 다른 문장 틀로 만듭니다.
3. **유형 판정은 사용자 입력만 씁니다.**
   - 고객 말씀과 메모에서 판정하고, 판정 근거 단어를 화면에 보여 줍니다.
   - 사용자가 유형을 직접 바꿀 수 있습니다.

## 구성

| 파일 | 역할 |
|---|---|
| `src/data/reportCategoryRules.ts` | 유형 판정 규칙(`REPORT_TEMPLATE_ALIASES`). 배열 순서가 우선순위이고, 고위험 유형을 먼저 봅니다. `detectReportCategoryDetailed`가 근거 단어와 함께 걸린 다른 유형도 돌려줍니다. |
| `src/utils/reportGenerator.ts` | 유형별 지식(`knowledge`)과 세 문서 생성 |
| `src/utils/reportQuality.ts` | 생성 결과 점검. 화면의 '작성 점검'과 자동 점검이 같은 규칙을 씁니다. |
| `src/utils/koreanJosa.ts` | 조사(을/를, 이/가 …)와 목록 잇기('A와 B', 'A, B 및 C') |
| `src/components/ReportGeneratorModal.tsx` | 입력 화면과 결과 탭 |
| `scripts/checkReports.ts` | 자동 점검 |

`reportGenerator.ts`의 유형별 지식 한 묶음에는 다음이 들어갑니다.

- 사내·고객사 표기
- 발생 내용 첫 줄
- 고객용 공감·확인·재발 방지 문장
- 사내 확인 계획
- 원인 후보
- 사내 재발 방지
- 고객사 확인 계획과 재발 방지

품질 유형의 '조리 상태 불량'(덜 익음 등)과 안전사고의 '부상'(화상·넘어짐 등)은 세부 갈래로 덮어씁니다.

새 유형은 다음 순서로 추가합니다.

1. `reportCategoryRules.ts`의 `ReportCategory`와 `REPORT_TEMPLATE_ALIASES`에 넣습니다.
2. `reportGenerator.ts`의 `knowledge`와 `reportCategoryOptions`에 넣습니다.
3. `reportQuality.ts`의 `categorySignature`에 넣습니다.
4. `scripts/checkReports.ts`의 `keywordFor`와 판정 사례에 넣습니다.

## 분량(짧게·보통·자세히)

| | 짧게 | 보통 | 자세히 |
|---|---|---|---|
| 사내 확인 계획 | 1개 | 2개 | 전부 |
| 사내 원인 후보 | 없음 | 2개 | 3개 |
| 사내 재발 방지 | 1개 | 2개 | 3개 |
| 고객사 보고 | 문단 3개 | ■ 항목별 | ■ 항목별 + 원인 미단정 문장 |
| 고객용 | 재발 방지 문단 생략 | 전체 | 전체 |

고위험 건은 분량과 상관없이 확인 항목을 모두 넣고 '중대' 기준으로 씁니다.

- 식중독 의심·안전사고
- 이물 혼입 중 유리·금속·철사·스테이플러 심·볼트·칼날처럼 다칠 수 있는 이물(`hazardousForeign`)
- 품질 중 상했거나 유통기한이 지난 음식(`spoiledFood`). '유통기한 확인 요청'처럼 문의만 한 경우는 제외합니다.
  이 경우 '변질·유통기한 경과 의심' 갈래로 바꿔, 제품 회수·유통기한·제조번호·동일 입고분·보관 온도 확인과 고객 몸 상태 확인을 씁니다.

## 자동 점검

```bash
npm run report:check   # 보고서
npm run search:check   # VOC 검색 (scripts/checkSearch.ts)
npm run menu:check     # 메뉴 추천 데이터·결과 (scripts/checkMenus.ts)
npm run check          # 세 가지 모두
```

다음 네 가지를 검사합니다.

1. **유형 판정:** 고객 표현 56개가 기대한 유형으로 판정되는지(오타·활용형·부정문·구어 화풀이 포함)
2. **조사:** 숫자·영문으로 끝나는 메뉴명을 포함한 조사 10개
3. **조합 전체:** 유형 × 완료 조치 × 진행 중 여부 × 고객 반응 × 분량 × 강도 × 메뉴 유무, 약 11만 개 조합에서 아래 규칙을 어기지 않는지
   - 고르지 않은 조치를 완료형으로 쓰지 않음
   - 고르지 않은 반응을 쓰지 않음
   - 문체가 섞이지 않음
   - 다른 유형의 상황 설명이 섞이지 않음
   - 자리표시가 남지 않음
   - 위험 표현이 없음
4. **점검 규칙 자체 검사:** 일부러 틀린 문장 15가지를 넣어 점검이 잡아내는지

`npm run report:check -- --print`를 실행하면 대표 사례 4개의 실제 문장도 출력합니다.
